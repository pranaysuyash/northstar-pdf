## The original claim, and what was actually wrong

The RG-134 record said "PDFKit drops checkbox values on 3 failing fixtures
(pdfkit-widgets, public-acroform, rotated-widget-90)" and proposed three
resolution paths, including "classify as known-excluded / reviewer
ratification". The investigation falsified the premise:

**PDFKit never dropped checkbox values.** Byte-level probes (`walkAcroForm` on
saved output, cross-read by qpdf) showed `buttonWidgetState` — the API the
shipped `PDFKitProvider.applyNativeValue` uses — round-tripped `/V` + `/AS`
correctly on **every** failing fixture. The failures were measurement
artifacts stacked in layers:

### Root causes found and fixed (in discovery order)

1. **Wrong write API in the experiment** (2026-09-05). The experiment wrote
   checkboxes through `setValue(_, forKey: .widgetValue)` while production
   uses `buttonWidgetState`. The `.widgetValue` write no-ops or reverts on
   several real encodings (public-sample-form uncheck; pdfkit-widgets
   noop/mutated check). Fix: route through `buttonWidgetState`, mirroring
   production.

2. **Hardcoded "Yes/Off" expectation** (2026-09-06). `generateTestValue`
   assumed the canonical vocabulary. For fixtures whose real on-token is
   `On`/`Checked`/`1`/`Y`/`True` (the 13 pikepdf-generated checkbox fixtures
   in `benchmark/datasets/checkbox-fixtures/` cover exactly this spread), the
   write was byte-correct but the read-back compared `Checked != Yes` — a
   phantom failure per non-Yes encoding. Fix: derive each field's on-token
   structurally from `/AP /N` keys minus `Off`; PDFKit cannot supply it
   (`buttonWidgetStateString` reports the on-token even when unchecked).

3. **Leading-slash token leakage** (2026-09-06). `buttonStates` carries
   `/AP /N` keys with their slash (`"/Yes"`); the derived on-token was
   `"/Yes"`, the write-side `isOn` check failed on `"/yes"`, deselecting
   every box. Moved checkbox 6v/12f → 16v/2f in one edit.

4. **PDFKit annotation-API `doc.write` drops `/Tx` when `/Btn` mutations
   happen in the same save** (verified, kept as a measured engine behavior).
   Mixed-type fixtures route through the production save path
   (`PDFIncrementalFormWriter.incrementalFieldUpdate`, the code
   `PDFKitProvider.exportAcroFormViaIncrementalWriter` ships) — as does any
   `/Tx`-bearing write, because `doc.write` drops pending text writes even on
   text-only fixtures (mutated.pdf `fullName` reads back "Grace Hopper" after
   a successful single-field probe on the same bytes). Pure `/Btn` fixtures
   keep the PDFKit API lane, which genuinely round-trips.

5. **Orphan widgets invisible to the writer** (production defect, fixed).
   `public-sample-form.pdf` carries `applicant.name`/`applicant.notes` with
   `/FT /Tx` + `/T` but only in the page `/Annots` array — not in AcroForm
   `/Fields`. `walkAcroFormModel` walked the field tree only, so
   `resolveEditPlan` threw `fieldNotFound` for fields PDFKit exposes (and
   that production users could try to edit). Fix: merge orphan page-annot
   widgets into the structural model, resolving indirect `/Annots` arrays
   (`/Annots 9 0 R` where obj 9 is the bare array) —
   `Sources/PDFEditorCore/PDFIncrementalFormWriter.swift`.

6. **Widget kids omit `/FT`** (fixed). Kid dicts inherit `/FT` from the
   parent; `checkboxOnToken` / `verifyCheckboxValueStructurally` required
   `fieldType == "Btn"` on the widget node and returned nil/false for
   merged-layout fixtures. Now match on FQN + `isWidget` + a button
   vocabulary.

7. **pdf-lib lane mirrored the same "Yes" hardcode** (fixed). The lane's
   `value === "Yes" ? cb.check() : cb.uncheck()` treated any non-Yes target
   as an uncheck request; its read-back hardcoded `isChecked ? "Yes" : "Off"`.
   Fixed to `check()` (pdf-lib applies the field's real on-token via
   `acroField.getOnValue()`) and to report the real token.

8. **Radio `/Opt` positional mapping** (spec finding, fixed). Per
   §12.7.5.4 Table 247, `/Opt` on a radio *parent* maps export values to
   widget kids **positionally**: kid *i*'s `/AP /N` state name may be
   producer-chosen (`/0` `/1`) and unrelated to the export (`email`
   `phone`). pdf-lib's `select()` is conformant; our readers were not.
   Fixed in `verifyRadioSelectionStructurally`, `qpdfReadBackAgrees`,
   `radioSelectionMatches` (with the caveat that PDFKit's
   `dataRepresentation()` **drops the radio parent's `/Opt`**, so the mapping
   must come from the original bytes), and the writer's `buttonEdits`
   (which previously threw `requestedStateUnavailable` for legal exports).
   `walkField` now parses `/Opt` for `Btn` fields, not just `Ch`.

9. **Pair-form `/Opt` display/export split** (measured, accepted). PDFKit
   and pdf-lib expose the *display* string through field APIs while `/V`
   carries the *export* (`Ground (5-7 days)` vs `ground`). Viewers read
   either form; the byte contract is gated separately by the structural
   check.

10. **qpdf text verifier vs duplicate `/V`** (inconclusive-read doctrine).
    Split field/widget layouts carry two `/V` copies; pdf-lib updates one and
    qpdf resolves the other. When the expected value exists as a `/V`
    anywhere in the bytes (literal or UTF-16BE hex), qpdf's single-object
    view is treated as inconclusive rather than a disagreement — same
    doctrine as "qpdf cannot see the group".

## What the IncrementalWriter radio "3 failures" actually are

Honest, fail-closed capability boundaries — not phantoms:

- `compressed-acroform.pdf` — source uses object streams
  (`WriterError.compressedObject`); the incremental writer operates on
  plain-xref files by design (RG-017 prefix invariant).
- `tagged-no-acroform.pdf` — no AcroForm dictionary in the catalog.
- `noop.pdf` — broken xref chain (`objectNotFound(2)`).

The writer refuses unparseable sources rather than corrupting them. Every
fixture it *can* parse verifies (13v, spec ✓).

PDFKit radio remains **experimental (spec-incomplete)**: its annotation API
omits the group `/V` on save (Observed 2026-09-03), so saved bytes fail the
§12.7.4.2.2 structural check even though the selection round-trips (16v/0f).
That is a real PDFKit writer deficiency, documented rather than papered over;
the production save path for AcroForm docs is the incremental writer, which
is spec-complete.

## Doctrine alignment

- **Measure, don't infer**: every row is executed by a genuinely independent
  engine (PDFKit native API, pdf-lib pure-JS lane, in-repo incremental
  writer, qpdf structural verifier) with four read-back channels
  (structural parser, pdf-lib reopen, qpdf JSON, PDFKit reopen).
- **Fail closed**: unreadable sources refuse (`compressedObject`,
  `malformedStructure`) instead of emitting corrupt output; unverifiable
  rows count as failures, not skips.
- **No known-exclusion escape hatch**: the "classify as known-excluded /
  reviewer ratification" path was not needed — the premise was false, and
  the real defects (including a production writer blind spot for orphan
  widgets) are fixed with regression guards in the gate report test.
