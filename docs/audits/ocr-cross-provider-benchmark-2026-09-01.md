## Results (Verified 2026-09-01)

### Apple Vision — Best overall
- **WER: 0.00%** (perfect on all 8 fixtures)
- **CER: 0.00%** (zero character errors)
- **Avg confidence: 93.75%**
- **Avg latency: 2,168ms**
- macOS native, no installation required
- Already wired in production (`VisionOCRProvider` in OCR.swift)

### Tesseract 5.5.0 — Best open-source baseline
- **WER: 0.0–1.9%** (near-perfect, 7/8 at 0%)
- **CER: 0.0–0.4%** (excellent)
- **Avg confidence: 94.2%**
- **Avg latency: 6,118ms** (cold first run; ~3s warm)
- Installed via Homebrew, Apache-2.0 license

### PaddleOCR PP-OCRv6 — Excellent on clean text, struggles with layout
- **WER: 0.0%** on 4/5 clean fixtures (clean-english, dense-paragraph, low-contrast, mixed-punctuation)
- **WER: 73.0%** on multi-column layout (reading order confusion)
- **CER: 0.0%** on clean text, 61.2% on multi-column
- **Avg confidence: 99.7%** (overconfident — high confidence even when WER is 73%)
- **Avg latency: 45,000ms** (~45s per fixture, model init adds ~20s first run)
- Requires `paddlepaddle` + `paddleocr` Python packages in venv
- Note: Multi-column failure is a known PaddleOCR limitation — single-column works perfectly
- **Decision:** Good fallback for single-column OCR; not suitable for complex layouts

## Known Limitations

1. **Corpus is small (8 fixtures)** — doesn't test multilingual, handwriting, complex layouts, or degraded scans
2. **PaddleOCR overconfidence** — reports 99.7% confidence even when WER is 73%. Confidence calibration is poor.
3. **Marker API instability** — `marker-pdf` v2.0 changed `ConfigParser` and `PdfConverter` APIs. Wrapper exists but not benchmarked end-to-end.
4. **No handwriting fixtures** — IAM dataset (87K lines) would be needed for handwriting evaluation
5. **No multilingual fixtures** — PaddleOCR's strength is multilingual; this corpus is English-only
6. **PaddleOCR multi-column failure** — reading order confusion on multi-column layouts; needs post-processing or layout-aware OCR

## Provider Architecture

### Swift (production)
- `VisionOCRProvider` in `OCR.swift` — used in production via `HybridOCRRouter`
- `TesseractProvider`, `PaddleOCRProvider`, `MarkerProvider` in `OCRCompanionBenchmark.swift` — benchmark-only

### Python (benchmark)
- `benchmark/compare_ocr_wer.py` — cross-provider WER benchmark (Tesseract, PaddleOCR, Vision)
- `benchmark/paddleocr_wrapper.py` — standalone PaddleOCR CLI wrapper
- `benchmark/marker_wrapper.py` — standalone Marker CLI wrapper (needs API fix)
- `benchmark/compare_ocr_providers.mjs` — Node.js benchmark (Tesseract, Vision, OCRmyPDF stubs, PDFBox stubs, MuPDF stub)

### CI Integration
- The cross-provider WER report is generated by `compare_ocr_wer.py`
- Results persisted at `benchmark/results/ocr-corpus/cross-provider-wer-report.json`
- Not yet wired as a CI gate (requires Python venv + paddlepaddle)

## Decision

**Apple Vision is the production OCR provider** — perfect accuracy, fast, no installation, native macOS.
**Tesseract is the fallback** — excellent accuracy (0–1.9% WER), Apache-2.0, cross-platform.
**PaddleOCR is a layout-dependent option** — perfect on single-column (0% WER), poor on multi-column (73% WER). Good for multilingual or when layout is simple.
**Marker is deferred** — API instability in v2.0; needs wrapper rewrite. Surya backend is promising for PDF→Markdown conversion.
**tesseract.js** — wired in browser lane (`compare_ocr_providers.mjs`), not benchmarked in Python lane.
